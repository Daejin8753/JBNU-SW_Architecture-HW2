이벤트 드리븐 경매 시스템

컴포넌트는 서로를 부르지 않습니다. 일어난 일을 이벤트로 브로커에 넣고, 그 토픽을 구독한 컴포넌트가 각자 자기 큐에서 꺼내 처리합니다. 아래 도면은 실제 코드(auction_eda.py)와 같은 규칙을 브라우저에서 다시 돌린 것입니다.

동작 흐름

입찰 하나가 낙찰이 되기까지

실행 한 번이 지나가는 순서입니다. 버튼을 누르면 위 도면에서 그 장면을 다시 보여 줍니다.

  1. 발행

    BidProducer가 입찰을 BidPlaced 봉투로 만들어 bid.placed에 넣고 바로 다음 입찰로 넘어갑니다. 누가 받는지, 처리가 끝났는지는 모릅니다.

  2. 팬아웃과 경쟁 소비자

    브로커는 bid.placed 구독 3곳(BidCapture·BidTracker·BidAnalytics)의 큐에 사본을 하나씩 넣습니다. BidAnalytics 큐 하나는 워커 2개가 나눠 꺼냅니다(성공 #1 11건, #2 5건).

  3. 만료 검사

    워커는 꺼낸 봉투의 TTL부터 봅니다. evt-0004·0012·0021은 TTL 0으로 발행돼 구독 3곳 모두에서 처리 없이 폐기됐습니다.

  4. 처리 사슬

    BidTracker는 최고가가 바뀔 때만 HighestBidChanged를 발행합니다. 이를 받아 Notifier는 알림을 보내고 Settlement는 최고가를 스스로 기억합니다. 최고가는 317 → 392 → 398원으로 3번 바뀌었습니다.

  5. 실패 격리

    BidAnalytics는 13의 배수 금액에서 일부러 실패합니다. 3번 재시도한 뒤 deadletter로 보내고, 같은 봉투를 받은 다른 구독자는 정상 처리합니다. 7건이 DLQ로 갔습니다.

  6. 마감과 낙찰

    모든 큐가 빈 뒤 AuctionClock이 AuctionClosed를 발행합니다. Settlement가 기억한 최고가로 영희 398원 낙찰을 확정해 AuctionSettled를 발행하고, Notifier가 낙찰 알림을 보냅니다.

커넥터

컴포넌트를 잇는 것은 토픽과 봉투뿐입니다

네 가지 커넥터

  • 토픽 (이벤트 채널) 6개bid.placed · bid.highest_changed · auction.closed · auction.settled · notification.sent · deadletter
  • publish / subscribe발행은 토픽 이름만 주면 끝나고, 구독은 listen() 한 줄로 붙습니다.
  • 구독별 비동기 큐같은 토픽이라도 구독마다 asyncio.Queue가 따로 있어서, 느린 BidAnalytics가 BidCapture를 막지 않습니다.
  • JSON 봉투 어댑터채널에는 객체가 아니라 JSON 문자열이 다닙니다. 넣을 때 dumps(), 꺼낼 때 loads().
broker.publish("bid.placed", "BidPlaced", payload)  # 즉시 반환
self.listen("bid.placed", self.handle, workers=2)    # 구독 + 워커 2개

한계

이 구조가 대신 내주는 것

흐름 제어와 순서 보장이 없음

브로커는 토픽 사이의 순서를 모릅니다. 실제 실행은 drain()으로 모든 큐가 빌 때까지 기다린 뒤 마감해 순서를 맞췄습니다. 이 대기를 빼고 BidTracker를 10ms 늦추면, 마감이 최고가보다 먼저 처리돼 유찰이 됩니다. 독립 테스트에서 실제로 재현했습니다.

복구성이 낮음

큐가 프로세스 메모리(asyncio.Queue)에만 있어서, 프로그램이 죽으면 처리 전 봉투가 모두 사라집니다. 실제 서비스라면 디스크에 남기는 영속 브로커와 처리 확인(ack) 기록이 필요합니다.
